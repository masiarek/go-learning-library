# `allocs/op` is a key, `ns/op` is not

**Level:** 301 · anyone who has pasted a benchmark table into a commit message

**One line:** A benchmark's `allocs/op` and `B/op` are decided by the code — eight string concatenations cost 8 allocations and 880 bytes, a `strings.Builder` with `Grow` costs 1 and 256 — and come out the same on every run and every machine; its `ns/op` is one sample of one machine on one afternoon, so a page keeps the counts as its answer key and shows the times as real runs.

Two ways to build an order line from eight fields, benchmarked with Go 1.24's `for b.Loop()`, and the first way once more with the loop every benchmark used before 1.24, `for i := 0; i < b.N; i++`. The script runs `go test -bench` with `-benchmem` and prints only the columns that cannot vary, plus a count of how many times each benchmark function was entered:

## Reading the output

**Eight fields, eight allocations, 880 bytes.** `line += f + ";"` concatenates three strings into a new one, and the runtime's [`concatstrings` ↗](https://github.com/golang/go/blob/go1.25.5/src/runtime/string.go) allocates that new string each time: eight fields, eight allocations. The bytes are the eight intermediate strings, each rounded up to the allocator's size class ([`sizeclasses.go` ↗](https://github.com/golang/go/blob/go1.25.5/src/internal/runtime/gc/sizeclasses.go)): 31 → 32, 55 → 64, 69 → 80, 94 → 96, 120 → 128, 134 → 144, 147 → 160 and 172 → 176 bytes, which sum to 880. That arithmetic is why the number is the same on arm64 and x86-64: the size classes are a table in the runtime, not a property of the machine.

**One allocation, 256 bytes, for the Builder.** `Grow(256)` allocates once, the writes fill the buffer, and [`String` ↗](https://github.com/golang/go/blob/go1.25.5/src/strings/builder.go) returns the bytes without copying them. The finished line is 172 bytes; the other 84 are slack the `Grow` asked for. Ask for the right amount and the count stays 1 while `B/op` drops.

**The old loop counts the same, and was entered twice.** `BenchmarkJoinWithPlusOldLoop` reports the same `880 B/op` and `8 allocs/op`, because the counts come from the code under test, not from the loop around it. The difference is in the `entered` lines: the two `b.Loop` benchmarks ran their function once each, the `b.N` benchmark twice — once with `b.N = 1`, to see how long an iteration takes, and once with the 2000 iterations that `-benchtime=2000x` asked for. [`B.Loop` ↗](https://pkg.go.dev/testing#B.Loop)'s documentation says it: `Loop` runs each benchmark function only once per measurement, whereas `b.N`-based benchmarks must run the benchmark function, and any setup and cleanup, several times. With the default one-second `-benchtime`, the demo below entered the old-style function 26 times for five counts.

**`ns/op` is not in the key, and neither is the iteration count.** Both are in the real runs below: 430–460 ns/op for the concatenation and 88–114 for the Builder on this machine, five runs each. They would be different numbers on the CI runners and on your laptop, and different again tomorrow. `allocs/op` and `B/op` would not.

The `-12` after each name is `GOMAXPROCS`, another machine fact the key strips. To see the table on your machine, run `bash demo/bench_table.sh` from this folder, or `bash demo/bench_table.sh 10` for ten counts.

**`-count`, `-benchtime` and `-benchmem`.** `-benchmem` adds the two allocation columns; `b.ReportAllocs()` inside a benchmark does the same for that one. `-benchtime=1s`, the default, runs each benchmark until about a second has passed; `-benchtime=2000x` runs exactly 2000 iterations, which is what keeps the key's run under a second. `-count=5` repeats each benchmark five times, so that the spread in `ns/op` is visible at all — and [`benchstat` ↗](https://pkg.go.dev/golang.org/x/perf/cmd/benchstat), from `golang.org/x/perf`, is the tool that turns two such sets of runs into a comparison with a confidence interval; it is outside the standard library and is not run here. The flags are listed under [`go help testflag` ↗](https://pkg.go.dev/cmd/go#hdr-Testing_flags).

## Why `b.Loop` replaced the `b.N` loop

The [Go 1.24 release notes ↗](https://go.dev/doc/go1.24#testingpkgtesting) give two reasons. The benchmark function executes exactly once per `-count`, so expensive setup and cleanup run once — the `entered` lines above. And function call parameters and results inside the loop are kept alive, so the compiler cannot optimise the loop body away; [`B.Loop` ↗](https://pkg.go.dev/testing#B.Loop)'s documentation adds that this is done by not inlining the functions called between the loop's braces, that it applies only to calls written there, and that the condition must be written exactly as `b.Loop()`. The old shape had neither property: setup before the loop ran on every calibration round, and a benchmark of a small pure function could report the time of an empty loop. The blog post [More predictable benchmarking with testing.B.Loop ↗](https://go.dev/blog/testing-b-loop) has the longer story, and [The compiler says what it inlines](../the_compiler_says_what_it_inlines/README.md) shows the inlining that `b.Loop` switches off.

```bash
#!/usr/bin/env bash
# A benchmark's allocs/op and B/op come out the same on every run and on every
# machine; its ns/op does not. This script runs `go test -bench` on two ways of
# building an order line and prints only the columns that cannot vary -- the
# benchmark names, B/op and allocs/op -- plus how many times each benchmark
# function was entered. The full table, ns/op included, is in demo/bench_table.sh.
set -u
export GOTOOLCHAIN=local

dir=$(mktemp -d)
trap 'rm -rf "$dir"' EXIT
cd "$dir" || exit 1

cat >line_test.go <<'GO'
package example

import (
	"fmt"
	"os"
	"strings"
	"testing"
)

var fields = []string{
	"customer=acme-industries",
	"item=steel-bracket-40mm",
	"quantity=1200",
	"warehouse=rotterdam-east",
	"carrier=overnight-freight",
	"priority=high",
	"currency=EUR",
	"reference=PO-2026-000418",
}

// joinWithPlus makes a new string for every field: one allocation each.
func joinWithPlus(fields []string) string {
	line := "order:"
	for _, f := range fields {
		line += f + ";"
	}
	return line
}

// joinWithBuilder asks for the room once; String() hands the bytes over
// without copying them.
func joinWithBuilder(fields []string) string {
	var b strings.Builder
	b.Grow(256)
	b.WriteString("order:")
	for _, f := range fields {
		b.WriteString(f)
		b.WriteByte(';')
	}
	return b.String()
}

// entered counts how many times each benchmark function was called.
var entered = map[string]int{}

func BenchmarkJoinWithPlus(b *testing.B) {
	entered[b.Name()]++
	for b.Loop() {
		joinWithPlus(fields)
	}
}

func BenchmarkJoinWithBuilder(b *testing.B) {
	entered[b.Name()]++
	for b.Loop() {
		joinWithBuilder(fields)
	}
}

// The loop shape every benchmark used before Go 1.24.
func BenchmarkJoinWithPlusOldLoop(b *testing.B) {
	entered[b.Name()]++
	for i := 0; i < b.N; i++ {
		joinWithPlus(fields)
	}
}

func TestMain(m *testing.M) {
	code := m.Run()
	for _, name := range []string{"BenchmarkJoinWithPlus", "BenchmarkJoinWithBuilder", "BenchmarkJoinWithPlusOldLoop"} {
		fmt.Printf("%s entered %d time(s)\n", name, entered[name])
	}
	os.Exit(code)
}
GO

say() { printf '$ %s\n' "$*"; }

say 'go mod init example'
go mod init example >/dev/null 2>&1 || exit 1

# -benchtime=2000x runs each loop exactly 2000 times, so this takes well under a
# second; the default is one second of iterations per benchmark.
say "go test -bench=. -benchmem -benchtime=2000x -run='^$' >bench.txt"
go test -bench=. -benchmem -benchtime=2000x -run='^$' >bench.txt 2>&1
status=$?

# Only the columns that cannot vary: drop the -N GOMAXPROCS suffix from the
# name, the iteration count and ns/op.
columns='/allocs\/op$/ { sub(/-[0-9]+$/, "", $1); printf "%-30s %5s B/op %3s allocs/op\n", $1, $(NF-3), $(NF-1) }'
say "awk '$columns' bench.txt"
awk "$columns" bench.txt

say "grep -E '^(PASS|FAIL|ok|Benchmark.* entered)' bench.txt"
grep -E '^(PASS|FAIL|ok|Benchmark.* entered)' bench.txt | sed -E 's/\t[0-9.]+s$//'
echo "exit status $status"
```

## What to do

- **Record the counts, show the times.** `allocs/op` and `B/op` belong in a test, a review comment or an answer key; `ns/op` belongs in a fence that names the machine, the Go version and the date.
- **Write `for b.Loop()`**, with setup above it and nothing else in the condition. The benchmark function then runs once, and the compiler cannot discard the calls inside.
- **Run with `-count` before believing a difference.** One run of each side is two samples; `-count=10` and `benchstat` is a comparison.
- **Pass `-benchmem`, always.** A change that halves `ns/op` and doubles `allocs/op` has moved the cost to the garbage collector; see [GOGC and GOMEMLIMIT tune the collector](../../14_Memory_and_the_Runtime/gogc_and_gomemlimit_tune_the_collector/README.md).
- **Never compare `ns/op` across machines**, and never across Go versions without re-running the old side.

## Practice

The page benchmarked two ways of building the line. Add a third, `strings.Join(fields, ";")` with the `order:` prefix and the closing `;` concatenated on, and report its `allocs/op` and `B/op` next to the other two — from a plain program rather than a test file. `testing.Benchmark` runs a benchmark function outside `go test` and returns a `BenchmarkResult` whose `AllocsPerOp` and `AllocedBytesPerOp` are the two columns; print those and the iteration count, and not `NsPerOp`.

```go
// Kata: report allocs/op and B/op for a third way of building the order line,
// strings.Join, from a plain program -- no test file. testing.Benchmark runs a
// benchmark function and returns a BenchmarkResult; the counts it holds are
// the same ones `go test -bench` prints. Nothing here prints a time.
//
//	go build allocs_per_op_is_a_key_ns_per_op_is_not_kata_go.go && ./allocs_per_op_is_a_key_ns_per_op_is_not_kata_go
package main

import (
	"flag"
	"fmt"
	"strings"
	"testing"
)

var fields = []string{
	"customer=acme-industries",
	"item=steel-bracket-40mm",
	"quantity=1200",
	"warehouse=rotterdam-east",
	"carrier=overnight-freight",
	"priority=high",
	"currency=EUR",
	"reference=PO-2026-000418",
}

func joinWithPlus(fields []string) string {
	line := "order:"
	for _, f := range fields {
		line += f + ";"
	}
	return line
}

func joinWithBuilder(fields []string) string {
	var b strings.Builder
	b.Grow(256)
	b.WriteString("order:")
	for _, f := range fields {
		b.WriteString(f)
		b.WriteByte(';')
	}
	return b.String()
}

// joinWithJoin lets strings.Join size the buffer, then concatenates once more
// for the prefix and the closing separator.
func joinWithJoin(fields []string) string {
	return "order:" + strings.Join(fields, ";") + ";"
}

func main() {
	// testing.Benchmark reads the -test.benchtime flag; outside `go test` the
	// flag has to be registered and set by hand. 1000x: exactly 1000 iterations.
	testing.Init()
	if err := flag.Set("test.benchtime", "1000x"); err != nil {
		panic(err)
	}
	candidates := []struct {
		name string
		join func([]string) string
	}{
		{"joinWithPlus", joinWithPlus},
		{"joinWithBuilder", joinWithBuilder},
		{"joinWithJoin", joinWithJoin},
	}
	for _, c := range candidates {
		result := testing.Benchmark(func(b *testing.B) {
			for b.Loop() {
				c.join(fields)
			}
		})
		fmt.Printf("%-16s iterations %d  %3d B/op  %d allocs/op\n", c.name, result.N, result.AllocedBytesPerOp(), result.AllocsPerOp())
	}
	fmt.Println("same line from all three:", joinWithPlus(fields) == joinWithBuilder(fields) && joinWithPlus(fields) == joinWithJoin(fields))
}
```

## In other languages

- The Rust library's [Benchmark harnesses ↗](https://masiarek.github.io/rust-learning-library/33_Time_and_Benchmarking/benchmark_harnesses/index.html) — what Criterion and Divan add on top of `Instant::now()`, which is roughly what `go test -bench` has built in; and [`black_box` is a hint ↗](https://masiarek.github.io/rust-learning-library/33_Time_and_Benchmarking/black_box_is_a_hint/index.html) — `std::hint::black_box` keeps a value alive by hand, which is what `b.Loop` does for call arguments and results by itself, and, as that page shows, it protects the value and not the way it was computed. [Timing a block ↗](https://masiarek.github.io/rust-learning-library/33_Time_and_Benchmarking/timing_a_block/index.html) is the one-sample measurement this page argues against.
- Python's [`timeit` ↗](https://docs.python.org/3/library/timeit.html) repeats a statement and reports the best of several runs; there is no allocation column, and [`tracemalloc` ↗](https://docs.python.org/3/library/tracemalloc.html) is the nearest thing. C's standard library has [`clock()` ↗](https://en.cppreference.com/w/c/chrono/clock) and no harness at all.
