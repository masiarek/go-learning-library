# `break` makes `yield` return false

**Level:** 301 · anyone writing an iterator that opens something and has to close it

**One line:** `break`, `return` and a panic in the loop body all end the producer's current call to `yield` — with `false`, or by unwinding through it — and the producer's deferred cleanup runs before the code after the loop does; a producer that calls `yield` again after a `false` panics with `range function continued iteration after function for loop body returned false`.

`Orders` yields three orders, prints what each `yield` returned, and defers a cleanup line that stands in for closing a file or releasing a lock. `main` ranges over it five times: with a `continue`, with a `break`, from inside `firstUrgent` which `return`s in the loop, with a panic in the body that `main` recovers, and with a `defer` written in the loop body.

## Reading the output

**`continue`: `yield("order-2") returned true`.** The body for order-2 printed nothing, but it finished, and a finished body is a `yield` that returns true. The producer went on to order-3 and returned on its own; the cleanup ran last.

**`break`: `yield("order-2") returned false`, then the cleanup, then the next section.** The [spec ↗](https://go.dev/ref/spec#For_range): if the loop body terminates, such as by a `break`, `yield` returns false and must not be called again. The producer saw the false, returned, its `defer` ran — and only then did `main` reach the line after the loop. Cleanup written in the producer is not skipped by a `break` in the consumer.

**`return` from `firstUrgent` looks the same to the producer.** The same `returned false`, the same cleanup, and only after both did `firstUrgent` hand `order-2` back. A `return` inside the body returns from the function around the loop, as it reads; the compiler's rewrite records the pending return, lets the producer finish, and performs it afterwards ([rewrite.go ↗](https://github.com/golang/go/blob/go1.25.5/src/cmd/compile/internal/rangefunc/rewrite.go)).

**A panic unwinds through the producer.** There is no `returned false` line for order-2: that `yield` call never returned at all. The panic unwound the producer's frame, running its deferred cleanup on the way, and reached `main`'s deferred `recover` with the value intact — the rule of [`recover` works only in the deferred call itself](../../13_Defer_Panic_and_Recover/recover_only_in_the_deferred_call_itself/README.md) holds across the iterator boundary.

**A `defer` in the loop body belongs to `main`.** The three deferred lines came after `the loop ended, main is still running`, last in first out, when `main` returned — not at the end of each run of the body, even though the body is compiled to a function of its own. The [wiki ↗](https://go.dev/wiki/RangefuncExperiment) states the rule: the semantics of `defer` do not depend on what kind of value is being ranged over, so this is the same as [`defer` in a loop runs at function end](../../13_Defer_Panic_and_Recover/defer_in_a_loop_runs_at_function_end/README.md). The fence at the end of this page shows the one case where go1.25.5 gets this wrong.

## The runtime checks how `yield` is used

The `yield` the compiler synthesizes keeps a state and refuses three things. One program, `misuse.go`, breaks one rule per argument, and each run has nothing to recover the panic:

**`careless`** calls `yield(2)` after `yield(1)` returned false. **`swallows`** recovers the loop body's panic inside the producer: the body's panic is the loop's to handle, and a producer that eats it would leave the loop with neither a value nor a panic, so the runtime panics for it. **`stashes`** keeps `yield` in a global and calls it after the loop is over. The messages are the runtime's own, from [`src/runtime/panic.go` ↗](https://github.com/golang/go/blob/go1.25.5/src/runtime/panic.go), and each program ends with exit status 2 like any other unrecovered panic ([A panic ends the whole program](../../01_Goroutines/a_panic_ends_the_whole_program/README.md)).

```go
// break, return and a panic in the loop body all end the iterator's call to
// yield -- with false, or by unwinding through it -- and the iterator's
// deferred cleanup runs before the code after the loop does. A defer written
// in the loop body belongs to the function around the loop, as it reads.
//
//	go build break_makes_yield_return_false_go.go && ./break_makes_yield_return_false_go
package main

import "fmt"

// Orders yields three orders and reports what each yield returned. Its
// deferred line stands in for a cleanup: closing a file, releasing a lock.
func Orders(yield func(string) bool) {
	defer fmt.Println("producer: deferred cleanup ran")
	for _, o := range []string{"order-1", "order-2", "order-3"} {
		ok := yield(o)
		fmt.Printf("producer: yield(%q) returned %t\n", o, ok)
		if !ok {
			return
		}
	}
}

// firstUrgent returns from inside the loop. To the iterator, that is a break.
func firstUrgent() string {
	for o := range Orders {
		if o == "order-2" {
			return o
		}
	}
	return "none"
}

func main() {
	fmt.Println("-- continue: yield returns true")
	for o := range Orders {
		if o == "order-2" {
			continue
		}
		fmt.Println("loop: got", o)
	}

	fmt.Println("-- break: yield returns false")
	for o := range Orders {
		fmt.Println("loop: got", o)
		if o == "order-2" {
			break
		}
	}

	fmt.Println("-- return from the enclosing function")
	fmt.Println("main: firstUrgent returned", firstUrgent())

	fmt.Println("-- panic in the loop body")
	func() {
		defer func() { fmt.Println("main: recovered:", recover()) }()
		for o := range Orders {
			if o == "order-2" {
				panic("cannot pack " + o)
			}
			fmt.Println("loop: got", o)
		}
	}()

	fmt.Println("-- defer in the loop body belongs to main")
	for o := range Orders {
		defer fmt.Println("main: deferred in the body for", o)
	}
	fmt.Println("main: the loop ended, main is still running")
}
```

```bash
#!/usr/bin/env bash
# Three ways to break the yield contract, in one program that takes the
# misuse as its argument, each run with nothing to recover the panic. The
# yield function the compiler synthesizes checks how it is used and panics
# with a message naming the misuse, and the program ends with exit status 2.
# The goroutine trace on stderr carries code offsets, so only the panic lines
# are kept.
set -u
export GOTOOLCHAIN=local

dir=$(mktemp -d)
trap 'rm -rf "$dir"' EXIT

cat >"$dir/misuse.go" <<'GO'
package main

import (
	"fmt"
	"os"
)

// Careless never looks at what yield returns.
func Careless(yield func(int) bool) {
	yield(1)
	yield(2)
}

// Swallows recovers a panic that came out of the loop body.
func Swallows(yield func(int) bool) {
	defer func() { recover() }()
	yield(1)
}

var saved func(int) bool

// Stashes keeps yield and calls it after the loop is over.
func Stashes(yield func(int) bool) {
	saved = yield
	yield(1)
}

func main() {
	switch os.Args[1] {
	case "careless":
		for n := range Careless {
			fmt.Println("loop: got", n)
			break
		}
	case "swallows":
		for range Swallows {
			panic("cannot pack this order")
		}
	case "stashes":
		for n := range Stashes {
			fmt.Println("loop: got", n)
		}
		fmt.Println("main: the loop is over")
		saved(2)
	}
}
GO

say() { printf '$ %s\n' "$*"; }

say 'go build misuse.go'
(cd "$dir" && go build misuse.go) || exit 1

for misuse in careless swallows stashes; do
	say "./misuse $misuse"
	(cd "$dir" && ./misuse "$misuse" 2>stderr.txt)
	status=$?
	grep 'panic:' "$dir/stderr.txt" | sed 's/^[[:space:]]*//'
	echo "exit status $status"
done
```

## When the function around the loop is an inlined literal

The `defer` rule above says: the function around the loop. In go1.25.5, when that function is a function literal small enough for the compiler to inline into its caller, the deferred call runs when the *caller* returns:

```text title="Real runs — go1.25.5, x86-64 Mac, 1 run each, 2026-09-23 (go1.25.14 in Docker, linux/amd64, printed the same)"
go version go1.25.5 darwin/amd64

go build  literal.go && ./literal
literal: loop ended, literal still running
main: the literal returned
literal: deferred in the body for 2
literal: deferred in the body for 1

go build -gcflags=-l literal.go && ./literal
literal: loop ended, literal still running
literal: deferred in the body for 2
literal: deferred in the body for 1
main: the literal returned
```

With inlining off (`-gcflags=-l`) the deferred lines come before `main: the literal returned`, where the rule puts them. A named function with the same body, and `main` itself as in the example above, behave correctly with inlining on. The example on this page keeps its loop in `main` for that reason. To see what your Go does, run `bash demo/inlined_literal_defer.sh` from this folder; the script builds the same program both ways. go1.25.14 on Linux printed the same eight lines. *(Not machine-checked here: the behaviour depends on an inlining decision, and a later Go may change it.)*

## What to do

- **Return from the iterator the moment `yield` returns false.** `if !yield(v) { return }` on every call; the runtime turns a forgotten check into a panic, but only at run time and only on a run that breaks early.
- **Put the cleanup in a `defer` inside the iterator.** Then `break`, `return` and a panic in the consumer all run it, and so does the sequence finishing on its own.
- **Do not `recover` inside an iterator.** A panic from the loop body belongs to the loop; an iterator that swallows it is refused by the runtime. If the producer itself can fail, yield an error value or return a `Seq2[V, error]`.
- **Never keep `yield` beyond the iterator's return** — not in a global, not in a goroutine. The loop's frame is gone when the iterator returns.

```go
// Kata: an iterator with a deferred cleanup, a search that returns from inside
// the loop, and a careless iterator caught by the runtime.
//
//	go build break_makes_yield_return_false_kata_go.go && ./break_makes_yield_return_false_kata_go
package main

import (
	"fmt"
	"iter"
	"slices"
)

// Batches yields orders in groups of size, and reports when it is done.
func Batches(orders []string, size int) iter.Seq[[]string] {
	return func(yield func([]string) bool) {
		defer fmt.Println("batches: cleanup ran")
		for start := 0; start < len(orders); start += size {
			end := min(start+size, len(orders))
			if !yield(orders[start:end]) {
				return
			}
		}
	}
}

// FirstBatchWith returns the first batch holding target. The return inside
// the loop makes yield return false inside Batches.
func FirstBatchWith(batches iter.Seq[[]string], target string) []string {
	for batch := range batches {
		if slices.Contains(batch, target) {
			return batch
		}
	}
	return nil
}

// Careless never looks at what yield returns.
func Careless(yield func(int) bool) {
	yield(1)
	yield(2)
}

func main() {
	orders := []string{"order-1", "order-2", "order-3", "order-4", "order-5"}
	fmt.Println("found:", FirstBatchWith(Batches(orders, 2), "order-3"))
	fmt.Println("found:", FirstBatchWith(Batches(orders, 2), "order-9"))

	defer func() { fmt.Println("recovered:", recover()) }()
	for n := range Careless {
		fmt.Println("got", n)
		break
	}
	fmt.Println("never printed")
}
```

## In other languages

- The Rust library's [Implementing `Iterator` ↗](https://masiarek.github.io/rust-learning-library/24_Iterators/implementing_iterator/index.html) — in Rust the consumer simply stops calling `next()`; nothing has to be told, because the producer is a value, not a running function. Cleanup is `Drop`, which runs when the iterator goes out of scope, whether the loop broke or finished. Go has no `Drop`, so the cleanup is a `defer` in the producer and `yield`'s result is the signal that fires it.
- Python's [`generator.close()` ↗](https://docs.python.org/3/reference/expressions.html#generator.close) is the same contract seen from the other side: closing a generator raises `GeneratorExit` at its suspended `yield`, its `finally` blocks run, and a generator that yields again after that is an error — the counterpart of `careless.go`.
