# A nil pointer in an interface is not nil

**Level:** 301 · anyone whose `if err != nil` fired on a call that had succeeded

**One line:** An interface value is `nil` only when it holds no type at all. A function that declares `var verr *ValidationError` and returns it as an `error` puts the type `*ValidationError` into the interface even when the pointer is nil — so the caller's `err != nil` is true, `%v` prints `<nil>` all the same, and `err.Error()` dereferences a nil pointer. Return a literal `nil`.

`validateTyped` is the bug and `validate` is the fix; both accept 10 and reject −5. The program prints, for each result, whether it equals `nil`, its `%T` and `%v`, what `reflect` sees, and what calling `Error()` does. `isNilPointerInside` is the diagnostic.

## Reading the output

**`validateTyped(10)`: `err == nil` is `false`, and `%T` says why.** The dynamic type is `*main.ValidationError`. An interface holds two words — a type and a value, as [An interface is two words](../an_interface_is_two_words/README.md) measures — and it compares equal to `nil` only when both are unset. `return verr` set the type word from the variable's static type, `*ValidationError`, and the value word to the nil pointer. The [Go FAQ ↗](https://go.dev/doc/faq#nil_error) has this exact case under "Why is my nil error value not equal to nil?"

**`%v` prints `<nil>` anyway.** That is the cruel part. `fmt` calls `Error()` on the value, the method dereferences its nil receiver and panics, and `fmt` catches the panic: [`print.go` ↗](https://github.com/golang/go/blob/go1.25.5/src/fmt/print.go), in `catchPanic`, prints `<nil>` for a nil pointer receiver rather than the panic. So the log line reads `error: <nil>`, and the reader concludes the error is nil. The `%T` line, or `err == nil` printed as a boolean, tells the truth.

**`err == (*ValidationError)(nil)` is `true`.** The comparison converts the typed nil to an `error` first — same type word, same nil pointer — and finds them equal. That is a way to test for this one type, but not a way to write `if err != nil`.

**`reflect` shows the two halves.** `reflect.ValueOf(err).Kind()` is `ptr` and `IsNil()` is `true`: the value is a pointer, and the pointer is nil. This is the diagnostic. Its one trap is that `reflect.ValueOf(nil)` returns the zero `Value`, on which [`IsNil` panics ↗](https://pkg.go.dev/reflect#Value.IsNil), so `isNilPointerInside` checks `err == nil` before it reflects.

**`err.Error()` panics.** `invalid memory address or nil pointer dereference` — the first line of code that trusts the error and reads `e.Field`. The panic is far from the `return verr` that caused it. A method written to tolerate a nil receiver hides this crash and keeps the wrong `!= nil`; the fix is at the return.

**`validate(10)` prints `<nil>` for `%T`.** A literal `nil` has no type: both words empty, `err == nil` is `true`. `validate(-5)` is an ordinary error, and the last three lines show the diagnostic separating all three cases.

// An interface value is nil only when it holds no type at all. A function
// that declares a *ValidationError variable and returns it puts the type
// *ValidationError into the error it returns even when the pointer is nil --
// so the caller's err != nil is true, %v prints <nil>, and calling Error()
// dereferences a nil pointer. The fix is to return a literal nil.
//
//	go build a_nil_pointer_in_an_interface_is_not_nil_go.go && ./a_nil_pointer_in_an_interface_is_not_nil_go
package main

import (
	"fmt"
	"reflect"
)

type ValidationError struct{ Field string }

func (e *ValidationError) Error() string { return "invalid " + e.Field }

// validateTyped returns its *ValidationError variable on every path. When the
// amount is fine the variable is a nil pointer -- and the error is not nil.
func validateTyped(amount int) error {
	var verr *ValidationError
	if amount < 0 {
		verr = &ValidationError{Field: "amount"}
	}
	return verr
}

// validate returns a literal nil on the good path: no type, no pointer.
func validate(amount int) error {
	if amount < 0 {
		return &ValidationError{Field: "amount"}
	}
	return nil
}

// isNilPointerInside reports an error that is non-nil only because it holds
// a typed nil pointer. reflect.ValueOf(nil) is the zero Value, and IsNil on
// that panics, so the err == nil check comes first.
func isNilPointerInside(err error) bool {
	if err == nil {
		return false
	}
	v := reflect.ValueOf(err)
	return v.Kind() == reflect.Pointer && v.IsNil()
}

func panicOf(f func()) (value any) {
	defer func() { value = recover() }()
	f()
	return "none"
}

func main() {
	err := validateTyped(10)
	fmt.Println("validateTyped(10):")
	fmt.Printf("  %-32s %t\n", "err == nil", err == nil)
	fmt.Printf("  %-32s %T\n", "%T", err)
	fmt.Printf("  %-32s %v\n", "%v", err)
	fmt.Printf("  %-32s %t\n", "err == (*ValidationError)(nil)", err == (*ValidationError)(nil))
	fmt.Printf("  %-32s %v, %t\n", "reflect Kind(), IsNil()", reflect.ValueOf(err).Kind(), reflect.ValueOf(err).IsNil())
	fmt.Printf("  %-32s %v\n", "err.Error() panicked with", panicOf(func() { _ = err.Error() }))

	err = validate(10)
	fmt.Println("validate(10):")
	fmt.Printf("  %-32s %t\n", "err == nil", err == nil)
	fmt.Printf("  %-32s %T\n", "%T", err)
	fmt.Printf("  %-32s %v\n", "%v", err)

	err = validate(-5)
	fmt.Println("validate(-5):")
	fmt.Printf("  %-32s %t\n", "err == nil", err == nil)
	fmt.Printf("  %-32s %T\n", "%T", err)
	fmt.Printf("  %-32s %v\n", "%v", err)

	fmt.Println("the diagnostic, over three results:")
	for _, e := range []error{validateTyped(1), validate(1), validate(-1)} {
		fmt.Printf("  isNilPointerInside %-5t  err == nil %-5t  %T\n", isNilPointerInside(e), e == nil, e)
	}
}

## What to do

- **Return `nil`, the literal, on the success path.** Declare the concrete pointer inside the branch that creates it — `return &ValidationError{...}` — and never hold a `*ValidationError` in a variable that reaches a `return` on the good path.
- **Give a function the return type `error`, not `*ValidationError`.** A function that returns the concrete pointer type makes every caller who writes `var err error = f()` produce a typed nil; [An error type with `Unwrap`](../../12_Errors/an_error_type_with_unwrap/README.md) keeps that convention for custom error types.
- **Print `%T` or `err == nil`, not `%v`, when an error looks nil and behaves otherwise.** `%v` reports `<nil>` for both the real thing and the trap.
- **No standard tool catches this.** It compiles and `go vet` is silent, as the vet page's [What no tool catches](../interfaces_vet_and_lints/README.md#what-no-tool-catches) records; [staticcheck's SA4023 ↗](https://staticcheck.dev/docs/checks/#SA4023) flags a comparison to `nil` that can never be true when it can see the typed return. Keep `isNilPointerInside` for tests and debugging, not for production code paths.

```go
// Kata: an order index has lookupTyped, written the typed-nil way, so every
// caller's err != nil fires even for an order that exists. Write diagnose(err)
// that returns "nil", "typed nil holding <type>" or "error: <message>", run
// it over the broken lookup and the fixed one, and print the verdicts.
//
//	go build a_nil_pointer_in_an_interface_is_not_nil_kata_go.go && ./a_nil_pointer_in_an_interface_is_not_nil_kata_go
package main

import (
	"fmt"
	"reflect"
)

type Order struct {
	ID    int
	Total int
}

type NotFoundError struct{ ID int }

func (e *NotFoundError) Error() string { return fmt.Sprintf("order %d not found", e.ID) }

var index = map[int]Order{7: {ID: 7, Total: 120}}

// lookupTyped declares the concrete pointer up front and returns it on both paths.
func lookupTyped(id int) (Order, error) {
	var notFound *NotFoundError
	order, ok := index[id]
	if !ok {
		notFound = &NotFoundError{ID: id}
	}
	return order, notFound
}

// lookup returns a literal nil when the order exists.
func lookup(id int) (Order, error) {
	order, ok := index[id]
	if !ok {
		return Order{}, &NotFoundError{ID: id}
	}
	return order, nil
}

func diagnose(err error) string {
	if err == nil {
		return "nil"
	}
	if v := reflect.ValueOf(err); v.Kind() == reflect.Pointer && v.IsNil() {
		return fmt.Sprintf("typed nil holding %T", err)
	}
	return "error: " + err.Error()
}

func main() {
	for _, id := range []int{7, 8} {
		_, err := lookupTyped(id)
		fmt.Printf("lookupTyped(%d): err != nil is %-5t  %s\n", id, err != nil, diagnose(err))
	}
	for _, id := range []int{7, 8} {
		_, err := lookup(id)
		fmt.Printf("lookup(%d):      err != nil is %-5t  %s\n", id, err != nil, diagnose(err))
	}
}
```

## In other languages

- The Rust library's [Nullable pointers ↗](https://masiarek.github.io/rust-learning-library/17_Option_and_Result/nullable_pointers/index.html) — Rust has no equivalent of this trap: a function returns `Result<T, E>`, an absent error is the `Ok` variant, and a `Box<dyn Error>` cannot be null, so there is no value that is "an error of type `E` holding nothing". The nearest thing, `Option<Box<dyn Error>>`, makes the absence a separate variant the caller must match.
- Java and C++ have null, but not a *typed* null hidden in a reference: a `Throwable` reference that is `null` is `null` whatever it was declared as ([the Java tutorial ↗](https://docs.oracle.com/javase/tutorial/java/javaOO/objectcreation.html)), and a `std::unique_ptr<Base>` holding `nullptr` is false in a condition. Go's interface carries the type separately from the pointer, and that second word is what `== nil` also reads.
