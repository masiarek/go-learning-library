# A method cannot have type parameters

**Level:** 301 · anyone who wrote `func (s *Stack[T]) Map[U any]` and met a syntax error

**One line:** A method's type parameters are its receiver's and no others — `Map[U]` on a `Stack[T]` is refused by the parser — so a transformation into a second type is a top-level function that takes the receiver as an argument, or a method on a second generic type that carries both parameters; the reason, in the FAQ and the proposal, is that a generic method could not be checked against an interface without instantiating it at run time.

The method that seems natural — turn a `Stack[T]` into a `Stack[U]` by applying a function to every item — needs a type parameter of its own, `U`, and that is the one thing a method may not declare:

## Reading the output

**A syntax error, not a type error.** Position `7:23` is the `[` after `Map`. The grammar in the [spec ↗](https://go.dev/ref/spec#Method_declarations) gives a method a receiver, a name and a signature, and no type parameter list of its own; the receiver's parameters, `T` here, are the only ones in scope. The parser stops before the type checker runs, which is why every other error on [the compiler errors page](../generics_compiler_errors/README.md) says something about types and this one says `syntax error`.

**Why.** The [FAQ ↗](https://go.dev/doc/faq#generics_methods) and the [proposal ↗](https://go.googlesource.com/proposal/+/refs/heads/master/design/43651-type-parameters.md#methods-may-not-take-additional-type-arguments) give the same reason. Go decides whether a type satisfies an interface by its method set, and a value's method can be called through an interface the compiler never saw the type together with. If a method could have its own type parameters, an interface could ask for `Map[U]`, and a call through that interface would need an instantiation for a `U` chosen at run time — either whole-program analysis at link time, run-time code generation, or giving up on interfaces working the same for every type. The proposal chose to forbid it and to recommend a top-level function instead; [issue 49085 ↗](https://github.com/golang/go/issues/49085), which gathered the case for lifting the rule, was closed as a duplicate in April 2026 without lifting it.

## The two workarounds

```text
Converter: main.Converter[int,float64] -> *main.Stack[float64] [3.5 6]
```

<!-- /output -->

**A top-level function that takes the receiver.** `MapStack[T, U any](s *Stack[T], f func(T) U)` has both parameters, and both are inferred at the call: `T` from `&orders`, `U` from the function literal's result. The `%T` line shows a `*main.Stack[int]` going in and a `*main.Stack[string]` coming out. This is the shape of the standard library: `slices.Map` does not exist as a method on anything, and [`slices` ↗](https://pkg.go.dev/slices) is a package of functions whose first argument is the collection.

**A second generic type whose method has both.** `Converter[T, U]` carries `U` as a parameter of the type, so its `Convert` method may use it — a method may use every parameter of its receiver's type. The cost is where `U` is fixed: at `Converter[int, float64]{…}`, when the value is made, rather than at each call. That is the right shape when the transformation is configured once and applied to many stacks, and the wrong one for a one-off.

## The receiver names its parameters

A near miss that looks like a specialization — a `Sum` only for `Stack[int]` — is really a declaration:

```text
./receiver_int.go:12:9: cannot use total (variable of type int) as int /* with int declared at ./receiver_int.go:7:16 */ value in return statement
```

<!-- /output -->

The identifiers in a receiver's brackets declare the method's type parameters, whatever they are called; they never select an instantiation ([FAQ ↗](https://go.dev/doc/faq#generics_receiver_type)). `Stack[int]` declares a type parameter named `int` that shadows the predeclared `int` inside the method, and the two messages are the compiler trying to say so: `mismatched types int and int /* with int declared at ./receiver_int.go:7:16 */`. Go has no specialization at all — the proposal lists it first under its [omissions ↗](https://go.googlesource.com/proposal/+/refs/heads/master/design/43651-type-parameters.md#omissions) — so a `Sum` for numeric stacks is, again, a top-level `SumStack[T Number](s *Stack[T]) T`, with the constraint from [A type parameter needs a constraint](../a_type_parameter_needs_a_constraint/README.md).

```bash
#!/usr/bin/env bash
# A method may use its receiver's type parameters, and may not declare any of
# its own. Stack[T].Map[U] is refused by the parser, before type checking.
set -u
export GOTOOLCHAIN=local

dir=$(mktemp -d)
trap 'rm -rf "$dir"' EXIT

cat >"$dir/generic_method.go" <<'GO'
package main

type Stack[T any] struct{ items []T }

// Map would turn a Stack[T] into a Stack[U] -- but U is the method's own
// type parameter, and a method may not have one.
func (s *Stack[T]) Map[U any](f func(T) U) *Stack[U] {
	out := &Stack[U]{}
	for _, v := range s.items {
		out.items = append(out.items, f(v))
	}
	return out
}

func main() {}
GO

say() { printf '$ %s\n' "$*"; }

say 'go build generic_method.go'
(cd "$dir" && go build generic_method.go) 2>&1
echo "exit status $?"
```

*[`a_method_cannot_have_type_parameters_go.go`](examples/a_method_cannot_have_type_parameters_go.go) in full — pasted here by `tools/run_examples.py` from the file CI runs.*

```go
// A method's only type parameters are its receiver's. A Stack[T] method may
// use T; to turn a Stack[T] into a Stack[U] a second parameter is needed, and
// it goes on a top-level function -- or on a second generic type, whose method
// then has both.
//
//	go build a_method_cannot_have_type_parameters_go.go && ./a_method_cannot_have_type_parameters_go
package main

import (
	"fmt"
	"strconv"
)

type Stack[T any] struct{ items []T }

func (s *Stack[T]) Push(v T) { s.items = append(s.items, v) }

// Items uses T, the receiver's parameter -- the one thing a method may use.
func (s *Stack[T]) Items() []T { return s.items }

// Workaround 1: a top-level generic function that takes the receiver as its
// first argument. T and U are both inferred at the call.
func MapStack[T, U any](s *Stack[T], f func(T) U) *Stack[U] {
	out := &Stack[U]{}
	for _, v := range s.items {
		out.Push(f(v))
	}
	return out
}

// Workaround 2: a generic type that carries both parameters, so that its
// method can use both. The price is that U is fixed when the Converter is
// made, not at each call.
type Converter[T, U any] struct{ f func(T) U }

func (c Converter[T, U]) Convert(s *Stack[T]) *Stack[U] {
	return MapStack(s, c.f)
}

func main() {
	var orders Stack[int]
	orders.Push(7)
	orders.Push(12)

	labels := MapStack(&orders, func(n int) string { return "order-" + strconv.Itoa(n) })
	fmt.Printf("MapStack:  %T -> %T %q\n", &orders, labels, labels.Items())

	halve := Converter[int, float64]{f: func(n int) float64 { return float64(n) / 2 }}
	halves := halve.Convert(&orders)
	fmt.Printf("Converter: %T -> %T %v\n", halve, halves, halves.Items())
}
```

## What to do

- **Put the extra type parameter on a top-level function that takes the receiver first**, `MapStack(s, f)`, and let inference fill both parameters at the call. It reads like the standard library's `slices` and `maps`.
- **Make it a generic type only when the transformation is configured once and applied many times** — a `Converter[T, U]` fixes `U` when it is built, which is a feature there and a nuisance elsewhere.
- **Name the receiver's parameters as the type declared them.** `func (s *Stack[T])` — never `Stack[int]`, which declares a parameter called `int`.
- **A method that needs an operation its receiver's constraint lacks** — `Sum` on a `Stack[T any]` — becomes a function with a narrower constraint, not a specialization.

## Practice

A `Stack[T]` needs a fold into a summary of another type — a total, a joined string, a count — and a method cannot introduce that second type. Write `ReduceStack[T, U any](s *Stack[T], start U, f func(U, T) U) U`, then a `Folder[T, U any]` type holding the start value and the function, whose `Fold(s *Stack[T]) U` method calls `ReduceStack`. Total a `Stack[int]` of quantities into an `int`, join a `Stack[string]` of names into one `string` with a `Folder[string, string]`, and count the same names with a `Folder[string, int]`; print each result with `%T` where the type is the point.

*[`a_method_cannot_have_type_parameters_kata_go.go`](examples/a_method_cannot_have_type_parameters_kata_go.go) in full — pasted here by `tools/run_examples.py` from the file CI runs.*

```go
// Kata: a fold over a Stack[T] into a summary of another type U. A method
// cannot introduce U, so the fold is written both ways a method cannot be: a
// top-level ReduceStack, and a Folder[T, U] type whose Fold method has both.
//
//	go build a_method_cannot_have_type_parameters_kata_go.go && ./a_method_cannot_have_type_parameters_kata_go
package main

import "fmt"

type Stack[T any] struct{ items []T }

func (s *Stack[T]) Push(v T) { s.items = append(s.items, v) }

// ReduceStack folds the items, bottom to top, into a U.
func ReduceStack[T, U any](s *Stack[T], start U, f func(U, T) U) U {
	acc := start
	for _, v := range s.items {
		acc = f(acc, v)
	}
	return acc
}

// Folder fixes the fold once; Fold then reads like the method that could not
// be written.
type Folder[T, U any] struct {
	start U
	f     func(U, T) U
}

func (r Folder[T, U]) Fold(s *Stack[T]) U { return ReduceStack(s, r.start, r.f) }

func main() {
	var quantities Stack[int]
	for _, q := range []int{4, 7, 10} {
		quantities.Push(q)
	}
	total := ReduceStack(&quantities, 0, func(acc, q int) int { return acc + q })
	fmt.Printf("ReduceStack: total quantity %d (%T)\n", total, total)

	var names Stack[string]
	names.Push("pear")
	names.Push("apple")
	joiner := Folder[string, string]{start: "", f: func(acc, n string) string {
		if acc == "" {
			return n
		}
		return acc + ", " + n
	}}
	fmt.Printf("Folder.Fold: %q (%T)\n", joiner.Fold(&names), joiner)

	count := Folder[string, int]{start: 0, f: func(acc int, _ string) int { return acc + 1 }}
	fmt.Println("Folder.Fold: count", count.Fold(&names))
}
```

## In other languages

- **Rust** — a generic method is ordinary: `impl<T> Stack<T> { fn map<U>(self, f: impl Fn(T) -> U) -> Stack<U> }`, because the compiler stamps out each instantiation it sees at compile time ([Static vs dynamic dispatch ↗](https://masiarek.github.io/rust-learning-library/12_Traits/static_vs_dynamic_dispatch/index.html)). Rust meets Go's wall only where it dispatches dynamically: a trait with a generic method cannot be made into a `dyn Trait` object, for the same reason — a vtable cannot hold an entry per possible `U`.
- **C++** — a member function template is allowed, and a virtual function cannot be a template ([cppreference ↗](https://en.cppreference.com/w/cpp/language/member_template)): the same restriction as Go's, drawn at the vtable instead of at the method.
- **Java** — `<U> Stack<U> map(Function<T, U> f)` is a generic method and may be part of an interface, because erasure leaves one method at run time whatever `U` is ([the Java tutorial ↗](https://docs.oracle.com/javase/tutorial/java/generics/methods.html)); Go instantiates rather than erases, and so cannot.
