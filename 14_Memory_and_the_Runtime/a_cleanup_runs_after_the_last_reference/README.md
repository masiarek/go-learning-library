# A cleanup runs after the last reference

**Level:** 301 · anyone wrapping a file descriptor, a C handle or a cache entry and wondering what happens when the wrapper is forgotten

**One line:** `runtime.AddCleanup` runs a function some time after an object becomes unreachable, and `weak.Pointer.Value` returns nil once it is gone; "unreachable" is decided by the last *use* in the code, not the end of a scope, so `runtime.KeepAlive` exists to be that use — and a cleanup on a tiny pointer-free object may wait for its neighbours.

A `Session` gets a weak pointer and a cleanup that reports its id on a channel. The program forces a collection while the session is still in use, then lets it go and collects until the cleanup reports; last, it does the same with the older `runtime.SetFinalizer`:

## Reading the output

**While `s` is in use, nothing happens.** `weak.Value()` returns the original pointer, and a full collection changes nothing: the cleanup has not run and the weak pointer is not nil. "In use" here is the `runtime.KeepAlive(s)` a few lines later — a use of `s` that the compiler must keep, so `s` is live across the `runtime.GC()` above it.

**After the last use, the collection finds the object dead.** `collectUntil` calls `runtime.GC()` and waits briefly for the channel, up to twenty times. [`AddCleanup` ↗](https://pkg.go.dev/runtime#AddCleanup) promises that the cleanup runs some time after the object is no longer reachable, in a separate goroutine — so a single `runtime.GC()` queues it but does not wait for it, and the loop is what makes the key honest. The weak pointer is nil by then: [`weak.Pointer.Value` ↗](https://pkg.go.dev/weak#Pointer.Value) returns nil once the object was reclaimed, and the collection that reclaimed it has finished when `runtime.GC()` returns.

**`s` is still in scope on the last line of `main`.** Nothing about scope kept it alive; only uses do. The version of this program first written had `s = nil` after the collection instead of `KeepAlive`, and the object was collected *before* that line in a few runs out of fifty — an assignment is not a use, so `s` was already dead at the `runtime.GC()`. That is the case [`runtime.KeepAlive` ↗](https://pkg.go.dev/runtime#KeepAlive) documents with a file descriptor: take `p.d` out of the wrapper, call `syscall.Read(p.d, ...)`, and without a `KeepAlive(p)` after it the finalizer may close the descriptor while `Read` is still on its way to the kernel.

**The finalizer ran, and was handed the object.** [`SetFinalizer` ↗](https://pkg.go.dev/runtime#SetFinalizer) calls `finalizer(obj)`: the object is reachable again for that call and is freed on a later cycle. A cleanup never sees the object — `AddCleanup` takes an argument of its own, and panics if that argument is the pointer itself, because an object reachable from its own cleanup can never become unreachable. The `SetFinalizer` documentation now says that new code should consider using `AddCleanup` instead, which is much less error-prone.

## The race `KeepAlive` prevents, seen

The runtime docs say the finalizer *could* run early; this demo takes `f.fd` out of a wrapper, forces two collections, and waits to see whether the cleanup gets there first:

```text title="Real runs — go1.25.5, x86-64 Mac, 50 runs, 2026-09-23"
go version: go1.25.5, 50 runs of race.go:
    44 runs printed closed before the fd was used: false
     6 runs printed closed before the fd was used: true
```

Six runs in fifty closed the descriptor before the code that held it was done. The count moves from run to run, which is why the example above shows the safe direction — with `KeepAlive`, never — and this fence shows the unsafe one. `bash demo/keepalive_race.sh` from this folder runs it on your machine.

## A cleanup on a tiny object may never run

An object of under 16 bytes that holds no pointers is a *tiny* allocation: the runtime packs several into one 16-byte block, and the block is freed only when every object in it is dead. The `SetFinalizer` documentation warns that the finalizer for an unreferenced object in such a block may never run if it always shares the block with a referenced object, and the same holds for cleanups. Three shapes, three objects each, twenty runs:

```text title="Real runs — go1.25.5, x86-64 Mac, 20 runs, 2026-09-23"
go version: go1.25.5, 20 runs of tiny.go:
    20 runs printed Sixteen {int, int64}: cleanups that ran out of 3: 3
    18 runs printed Tiny {int}: cleanups that ran out of 3: 0
     2 runs printed Tiny {int}: cleanups that ran out of 3: 3
    20 runs printed WithString {int, string}: cleanups that ran out of 3: 3
```

A `struct{ fd int }` lost all three cleanups in eighteen runs of twenty; the same struct with a `string` beside the descriptor, or a second 8-byte field, ran all three every time. The kata below gives its `Connection` an address for exactly this reason. `bash demo/tiny_objects.sh` reproduces the table.

```go
// runtime.AddCleanup attaches a function that runs some time after the
// object becomes unreachable; weak.Make gives a pointer that does not keep
// it alive. Neither happens while the object is still in use, and "in use"
// means a later use in the code, not the end of a scope: runtime.KeepAlive
// is that later use. runtime.SetFinalizer is the older mechanism.
//
//	go build a_cleanup_runs_after_the_last_reference_go.go && ./a_cleanup_runs_after_the_last_reference_go
package main

import (
	"fmt"
	"runtime"
	"time"
	"weak"
)

type Session struct {
	id  int
	buf []byte
}

// collectUntil runs the collector until done receives, at most tries times.
// A cleanup runs in its own goroutine some time after the collection that
// found the object dead, so one runtime.GC() is not a guarantee.
func collectUntil(done <-chan int, tries int) (int, bool) {
	for range tries {
		runtime.GC()
		select {
		case id := <-done:
			return id, true
		case <-time.After(50 * time.Millisecond):
		}
	}
	return 0, false
}

func main() {
	closed := make(chan int, 1)
	s := &Session{id: 7, buf: make([]byte, 1024)}
	w := weak.Make(s)
	runtime.AddCleanup(s, func(id int) { closed <- id }, s.id)
	fmt.Println("weak.Value() while s is in use:", w.Value() == s)

	runtime.GC()
	time.Sleep(20 * time.Millisecond)
	fmt.Println("after a GC while s is still in use: cleanup ran:", len(closed) > 0, " weak is nil:", w.Value() == nil)
	runtime.KeepAlive(s) // the last use of s: it was reachable up to here

	id, ok := collectUntil(closed, 20)
	fmt.Println("after the last use of s: cleanup ran:", ok, " with id:", id)
	fmt.Println("weak pointer is nil:", w.Value() == nil)

	// The older mechanism hands the finalizer the object itself.
	finalized := make(chan int, 1)
	old := &Session{id: 8}
	runtime.SetFinalizer(old, func(o *Session) { finalized <- o.id })
	id, ok = collectUntil(finalized, 20)
	fmt.Println("finalizer ran:", ok, " with id:", id)
}
```

## What to do

- **Close things explicitly** — `defer f.Close()` — and attach a cleanup as the backstop for the caller who forgot. `AddCleanup` says outright that a cleanup is not guaranteed to run before the program exits, so it can never be the way a buffer gets flushed.
- **Give the cleanup its own argument, never the object.** The descriptor, the handle, the key: whatever the cleanup needs, copied out at `AddCleanup` time. Reaching the object from the cleanup or its argument keeps it alive forever.
- **`runtime.KeepAlive(obj)` after the last use of anything taken out of `obj`** — a descriptor, an `unsafe.Pointer`, a C handle — so that the cleanup cannot run in the middle of the call that uses it.
- **Prefer `AddCleanup` and `weak.Make` to `SetFinalizer`**; the [GC guide ↗](https://go.dev/doc/gc-guide#Finalizers_cleanups_and_weak_pointers) lists what goes wrong with each.
- **Make the object big enough to own its block** — a pointer field or 16 bytes — when its cleanup matters, and **test object death** the way the example does: drop, `runtime.GC()`, wait, repeat, with a bound.

```go
// Kata: a Connection wraps a file descriptor. Give every Connection a
// cleanup that records the descriptor it closed. Open three, cancel the
// cleanup of the second with Cleanup.Stop, drop all three, collect, and
// print the descriptors that were closed, sorted, and that the stopped
// one was not.
//
//	go build a_cleanup_runs_after_the_last_reference_kata_go.go && ./a_cleanup_runs_after_the_last_reference_kata_go
package main

import (
	"fmt"
	"runtime"
	"slices"
	"time"
)

// Connection holds a string as well as the descriptor. A struct of one int
// would be a "tiny", pointer-free object, which the runtime packs into a
// shared 16-byte block whose cleanups wait for every object in the block.
type Connection struct {
	fd   int
	addr string
}

var closed = make(chan int, 8)

func open(fd int, addr string) (*Connection, runtime.Cleanup) {
	c := &Connection{fd: fd, addr: addr}
	return c, runtime.AddCleanup(c, func(fd int) { closed <- fd }, fd)
}

// collect runs the collector until want descriptors have been reported, or
// gives up after tries rounds.
func collect(want, tries int) []int {
	var fds []int
	for range tries {
		runtime.GC()
		for len(fds) < want {
			select {
			case fd := <-closed:
				fds = append(fds, fd)
				continue
			case <-time.After(50 * time.Millisecond):
			}
			break
		}
		if len(fds) == want {
			break
		}
	}
	slices.Sort(fds)
	return fds
}

func main() {
	first, _ := open(3, "db-1:5432")
	second, stop := open(4, "cache-1:6379")
	third, _ := open(5, "db-2:5432")
	stop.Stop()
	fmt.Println("open:", first.fd, second.fd, third.fd, " cleanup of 4 stopped")
	// No use of first, second or third after this line: all three are dead.

	fmt.Println("closed after collection:", collect(2, 20))
	runtime.GC()
	time.Sleep(50 * time.Millisecond)
	fmt.Println("the stopped cleanup reported anything:", len(closed) > 0)
}
```

## In other languages

- **Rust** — the Rust library's [Assignment drops the old value ↗](https://masiarek.github.io/rust-learning-library/18_Ownership/assignment_is_a_drop/index.html): `Drop` runs at a point the code determines — the end of the scope, or the assignment that overwrites — where Go's cleanup runs "some time after"; [`Rc`: the clone that copies a pointer ↗](https://masiarek.github.io/rust-learning-library/18_Ownership/reference_counting/index.html) has `Weak`, the counted counterpart of `weak.Pointer`, whose `upgrade` returns `None` the way `Value` returns nil.
- **Java** — [`java.lang.ref.Cleaner` ↗](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/ref/Cleaner.html) has the same shape as `AddCleanup`: a cleaning action that must not reference the object, run by a background thread after the object becomes phantom-reachable, with `finalize` deprecated behind it as `SetFinalizer` is here.
- **Python** — reference counting frees an object the moment its last reference goes, so `__del__` usually runs at once; [`weakref` ↗](https://docs.python.org/3/library/weakref.html) has the weak references and `finalize`, and cycles wait for the cycle collector.
