# A goroutine stack grows and has a limit

**Level:** 301 · anyone who has watched a recursive function die in another language, or wondered how a million goroutines fit in memory

**One line:** A goroutine begins with a small stack that the runtime copies into a bigger one as the calls nest, so a descent a million frames deep succeeds; the limit is 1,000,000,000 bytes on a 64-bit machine, `debug.SetMaxStack` returns it, and crossing it is a fatal error that no `recover` can catch.

The program reads the limit, then starts a goroutine that recurses a million calls deep, reads the runtime's stack accounting at the bottom, and reports how much the stack grew:

## Reading the output

**The limit is 1000000000, not 1 GiB.** [`debug.SetMaxStack` ↗](https://pkg.go.dev/runtime/debug#SetMaxStack) documents the initial setting as 1 GB on 64-bit systems and 250 MB on 32-bit ones, and returns the previous setting. The value is the decimal billion: [`runtime/proc.go` ↗](https://github.com/golang/go/blob/go1.25.5/src/runtime/proc.go) sets `maxstacksize = 1000000000` with the comment that decimal looks nicer in the failure message. The second call sets it back and returns the 64 MiB that the first call had set.

**A million frames, one goroutine.** `dive` is a plain recursive function. Its frame is a few dozen bytes, so a million of them are tens of megabytes, far under the limit — and far over the 8 MB that a thread's stack gets by default on most systems. The goroutine did not start with tens of megabytes: a goroutine's stack starts at 2 KB (`stackMin` in [`runtime/stack.go` ↗](https://github.com/golang/go/blob/go1.25.5/src/runtime/stack.go), the size the [Go 1.4 release notes ↗](https://go.dev/doc/go1.4#runtime) reduced it to) and, since Go 1.19, at a size the runtime adapts to the average of recent goroutines. *(Not machine-checked here.)*

**It grew by more than 8 MB.** `MemStats.StackInuse` is the memory the runtime currently holds in goroutine stacks. Read before the goroutine started and again at the bottom of the descent, it grew by more than 8 MB — on this machine by 32 MB, a 32-byte frame a million times, rounded up to a power of two. The frame size differs between amd64 and arm64, so the key records only a threshold that any frame clears: even a 16-byte frame, the smallest a return address and a saved frame pointer allow, makes 16 MB.

**How it grows.** Every function's prologue compares the stack pointer against the goroutine's guard; when the next frame would not fit, it calls `morestack`, and the runtime allocates a stack twice the size, copies the old one into it and adjusts every pointer that pointed into the old stack (`copystack` and `adjustpointers`, in the same file). The stack is one contiguous block, always — there are no linked segments to hop between, which is what made the 2014 design faster than the one before it.

## Past the limit

The runtime cannot copy a stack that would exceed the limit, so it stops the program. The driver lowers the limit to 1 MiB so that the overflow comes at once, and keeps the two lines of stderr that do not carry addresses:

**`fatal error`, not `panic`.** The message comes from `runtime.throw`, and a throw is not a panic: no deferred function runs, no `recover` sees it, and the process exits with status 2 after printing every goroutine's stack — a trace that for this program is a million lines of `main.dive`, most of them elided. [`recover` works only in the deferred call itself](../../13_Defer_Panic_and_Recover/recover_only_in_the_deferred_call_itself/README.md) covers what a `recover` can and cannot catch; a stack overflow is on the cannot side, the same as a deadlock ([All goroutines are asleep](../../02_Channels/all_goroutines_are_asleep/README.md)).

**The number in the message is the limit, in bytes.** With the default it reads `exceeds 1000000000-byte limit`; here it is the 1048576 the program set. `SetMaxStack` limits future growth only, so a goroutine that is already past a newly lowered limit keeps running until it needs to grow again.

## Why nothing outside a goroutine may point into its stack

A copy moves every frame to a new address. The runtime finds and fixes the pointers it knows about — those in the stack's own frames, whose layout the compiler recorded, and those in the goroutine's own runtime structures. A pointer held anywhere else — in another goroutine, in a global, in C memory — would point at the old, freed stack. That is the reason behind two rules elsewhere in this library: escape analysis moves any variable whose address may outlive its frame to the heap ([Escape analysis decides stack or heap](../escape_analysis_decides_stack_or_heap/README.md)), and cgo forbids C code from keeping a Go pointer after the call returns ([cgo, "Passing pointers" ↗](https://pkg.go.dev/cmd/cgo#hdr-Passing_pointers)).

**Frame size is what a million multiplies.** While this page was being written, a version of `dive` had `stackInUse` inlined into it, and the `runtime.MemStats` value inside — several kilobytes — became part of every frame: a million of those overran the 1 GB limit, on the same machine and the same depth. Marking `stackInUse` with `//go:noinline` keeps the big value in one frame. *(Not machine-checked here.)*

```go
// A goroutine's stack starts small and grows as the calls nest: a descent a
// million frames deep succeeds, and the runtime's stack accounting shows
// the growth. debug.SetMaxStack returns the previous limit, which is
// 1000000000 bytes on a 64-bit machine.
//
//	go build a_goroutine_stack_grows_and_has_a_limit_go.go && ./a_goroutine_stack_grows_and_has_a_limit_go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
)

// stackInUse reads the bytes the runtime currently holds in goroutine
// stacks. It is not inlined: MemStats is several kilobytes, and inlined
// into dive it would be part of every one of the million frames.
//
//go:noinline
func stackInUse() uint64 {
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	return m.StackInuse
}

var atTheBottom uint64

// dive recurses until depth reaches target and reads the stack size there.
func dive(depth, target int) int {
	if depth == target {
		atTheBottom = stackInUse()
		return depth
	}
	return dive(depth+1, target)
}

func main() {
	fmt.Println("SetMaxStack(64<<20) returned the default limit:", debug.SetMaxStack(64<<20))
	fmt.Println("SetMaxStack(1000000000) returned what was just set:", debug.SetMaxStack(1000000000))

	before := stackInUse()
	reached := make(chan int)
	go func() { reached <- dive(0, 1000000) }()
	fmt.Println("depth reached:", <-reached)
	fmt.Println("stack in use grew by more than 8 MB during the descent:", atTheBottom-before > 8<<20)
}
```

#!/usr/bin/env bash
# A goroutine that grows its stack past the limit is not a panic that can be
# recovered: the runtime prints "fatal error: stack overflow" and the process
# exits with status 2. The program lowers the limit to 1 MiB with
# debug.SetMaxStack so that the overflow comes quickly. The stderr also
# carries stack addresses and a goroutine trace with a temporary path, so
# this script keeps only the two lines that name the failure.
set -u
export GOTOOLCHAIN=local

dir=$(mktemp -d)
trap 'rm -rf "$dir"' EXIT

cat >"$dir/overflow.go" <<'GO'
package main

import (
	"fmt"
	"runtime/debug"
)

// dive never reaches a base case; each call adds a frame.
func dive(depth int) int {
	return dive(depth+1) + 1
}

func main() {
	debug.SetMaxStack(1 << 20)
	fmt.Println("limit set to 1 MiB, recursing without end")
	fmt.Println(dive(0))
}
GO

say() { printf '$ %s\n' "$*"; }

say 'go build overflow.go'
(cd "$dir" && go build overflow.go) || exit 1

say './overflow'
(cd "$dir" && ./overflow 2>stderr.txt)
status=$?
grep -E '^runtime: goroutine stack exceeds|^fatal error: stack overflow' "$dir/stderr.txt"
echo "exit status $status"
```

## What to do

- **Recurse freely over data that is deep** — a tree, a parser's nesting, a linked list — and give a runaway recursion a base case rather than a bigger limit. `SetMaxStack` is for limiting damage, as its documentation says, not for making room.
- **Do not size goroutine stacks in your head.** They start small and grow on demand; the cost of a goroutine is its stack's current size, which is why [Goroutines are cheap](../../01_Goroutines/goroutines_are_cheap/README.md) can start so many.
- **Keep large values out of recursive frames.** A big array or struct declared inside a recursive function is copied into every frame; allocate it once outside, or pass a pointer.
- **Treat a stack overflow like any other `fatal error`**: it ends the process, so a server that recurses over untrusted input needs a depth check, not a `recover`.

// Kata: sum a linked list of 500,000 invoices with a plain recursive
// function, the kind that would overflow a fixed 8 MB stack in C at a few
// dozen bytes a frame. Print the count and the total, and show that the
// stack limit you set for the goroutine is the one SetMaxStack hands back
// on the next call.
//
//	go build a_goroutine_stack_grows_and_has_a_limit_kata_go.go && ./a_goroutine_stack_grows_and_has_a_limit_kata_go
package main

import (
	"fmt"
	"runtime/debug"
)

type Invoice struct {
	Cents int64
	Next  *Invoice
}

// sum is deliberately recursive: one frame per invoice.
func sum(inv *Invoice) (count int, cents int64) {
	if inv == nil {
		return 0, 0
	}
	count, cents = sum(inv.Next)
	return count + 1, cents + inv.Cents
}

func main() {
	var head *Invoice
	for i := 1; i <= 500000; i++ {
		head = &Invoice{Cents: int64(i%100) + 1, Next: head}
	}

	previous := debug.SetMaxStack(256 << 20)
	fmt.Println("limit before the kata, bytes:", previous)
	count, cents := sum(head)
	fmt.Println("invoices:", count, " total cents:", cents)
	fmt.Println("SetMaxStack hands back the 256 MiB that was set:", debug.SetMaxStack(previous) == 256<<20)
}
```

## In other languages

- **Concurrency library** — [How many threads can you start? ↗](https://masiarek.github.io/concurrency-learning-library/01_Threads/how_many_threads_can_you_start/index.html) measures the other side of this page: an operating-system thread reserves megabytes of stack up front, and the machine runs out in the tens of thousands, where goroutines start with kilobytes and run into the millions. [What is a goroutine, if not a thread? ↗](https://masiarek.github.io/concurrency-learning-library/01_Threads/a_goroutine_is_not_a_thread/index.html) puts the two side by side.
- **Rust** — the Rust library's [Recursion and the size of the stack ↗](https://masiarek.github.io/rust-learning-library/18_Ownership/recursion_and_the_stack/index.html): a Rust thread's stack is fixed at spawn time — 8 MB for the main thread, 2 MB for others unless `thread::Builder::stack_size` says otherwise — and a stack overflow aborts the process with a signal, not a message with a byte count. [The call stack: what a call does to memory ↗](https://masiarek.github.io/rust-learning-library/18_Ownership/the_call_stack/index.html) draws the frames this page multiplies by a million.
- **C** — the stack is whatever `ulimit -s` or [`pthread_attr_setstacksize` ↗](https://man7.org/linux/man-pages/man3/pthread_attr_setstacksize.3.html) gave the thread, and running past it is a segmentation fault with no runtime to name the cause.
