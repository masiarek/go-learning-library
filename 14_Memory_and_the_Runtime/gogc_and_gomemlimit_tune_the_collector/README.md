# GOGC and GOMEMLIMIT tune the collector

**Level:** 301 · anyone running Go in a container with a memory cap, or wondering why the collector runs when it does

**One line:** The collector has two knobs and no more: `GOGC` says how much new heap a collection waits for (100 by default — run again when the live heap has doubled), and `GOMEMLIMIT` puts a soft ceiling on the runtime's total memory; `debug.SetGCPercent` and `debug.SetMemoryLimit` set them from inside and return the previous value, and with the collector switched off only the limit can start a collection.

The program reads and sets both knobs, forces a collection, then allocates 256 MiB of garbage twice: once with the collector off and no limit, once with the collector off and a 64 MiB limit.

## Reading the output

**Both setters return the previous value, and `SetMemoryLimit(-1)` only asks.** [`SetGCPercent` ↗](https://pkg.go.dev/runtime/debug#SetGCPercent) returns 100, the default, and then 50, what was just set. [`SetMemoryLimit` ↗](https://pkg.go.dev/runtime/debug#SetMemoryLimit) with a negative argument leaves the limit as it is and returns it: `math.MaxInt64`, which is the runtime's way of saying no limit. `SetGCPercent` has no query form — to read it, set it and set it back, as the kata does.

**`runtime.GC()` runs a full cycle now.** `MemStats.NumGC` counts completed cycles, and it went up. [`runtime.GC` ↗](https://pkg.go.dev/runtime#GC) blocks until the collection is complete, sweep included, which is why the next lesson can use it to make an object's death observable.

**Collector off, no limit: 256 MiB of garbage and no collection.** `SetGCPercent(-1)` is `GOGC=off`. The pacer never triggers on heap growth, and the two-minute forced collection is skipped as well — [`runtime/mgc.go` ↗](https://github.com/golang/go/blob/go1.25.5/src/runtime/mgc.go) returns false from the time trigger when the percent is negative. The garbage sits there; `NumGC` did not move. In a program that keeps allocating, that is memory growth without end.

**Collector off, 64 MiB limit: a collection ran.** The limit is the second trigger, independent of the first. When the runtime's total memory — heap, stacks, and its own structures, not the binary or memory held by C — approaches the limit, it collects whatever `GOGC` says. This is the combination the [Go 1.19 design ↗](https://github.com/golang/proposal/blob/master/design/48409-soft-memory-limit.md) was made for: `GOGC=off` with a `GOMEMLIMIT` lets a program use all the memory it has been given and collect only when it must. The limit is soft: the [GC guide ↗](https://go.dev/doc/gc-guide#Memory_limit) explains that the runtime will let the heap exceed it rather than let the collector take more than about half of the CPU, so it caps a leak's rate, not a leak.

**Restoring.** `SetMemoryLimit(-1)` now reports the 64 MiB; `SetGCPercent(100)` returns the `-1` that was in force. A library that changes either setting should put back what it found, as the kata's helper does.

The three numbers before `MB` are the heap at the start of the cycle, at its end, and the live heap that survived; the `goal` is where the next cycle will start. With a 2 MB live heap and `GOGC=100` the goal is about 4 MB and 256 MiB of garbage takes a hundred cycles; `GOGC=25` sets the goal a quarter above the live heap and takes 253; with the collector off and a 32 MiB limit the goal is the limit less the runtime's other memory, 26 MB, and ten cycles do the same work. Fewer cycles cost more memory, and the other way round — the trade `GOGC` sets. To see it on your machine, run `bash demo/gctrace.sh` from this folder.

```go
// The two knobs of the collector, read and set from inside the program.
// debug.SetGCPercent and debug.SetMemoryLimit each return the previous
// setting; runtime.GC forces a cycle; with the collector off, garbage is
// never collected until a memory limit says it must be.
//
//	go build gogc_and_gomemlimit_tune_the_collector_go.go && ./gogc_and_gomemlimit_tune_the_collector_go
package main

import (
	"fmt"
	"math"
	"runtime"
	"runtime/debug"
)

// numGC is the number of completed collections since the program started.
func numGC() uint32 {
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	return m.NumGC
}

var slab []byte

// churn allocates total bytes in 1 MiB slabs and drops each one.
func churn(total int) {
	for range total >> 20 {
		slab = make([]byte, 1<<20)
	}
	slab = nil
}

func main() {
	fmt.Println("SetGCPercent(50) returned the default:", debug.SetGCPercent(50))
	fmt.Println("SetGCPercent(100) returned what was just set:", debug.SetGCPercent(100))
	fmt.Println("SetMemoryLimit(-1) leaves the limit alone and returns math.MaxInt64:", debug.SetMemoryLimit(-1) == math.MaxInt64)

	before := numGC()
	runtime.GC()
	fmt.Println("runtime.GC() increased NumGC:", numGC() > before)

	fmt.Println("SetGCPercent(-1) turns the collector off; it returned:", debug.SetGCPercent(-1))
	before = numGC()
	churn(256 << 20)
	fmt.Println("collector off, no limit: 256 MiB of garbage ran a collection:", numGC() > before)

	fmt.Println("SetMemoryLimit(64<<20) returned math.MaxInt64:", debug.SetMemoryLimit(64<<20) == math.MaxInt64)
	before = numGC()
	churn(256 << 20)
	fmt.Println("collector off, 64 MiB limit: 256 MiB of garbage ran a collection:", numGC() > before)

	fmt.Println("SetMemoryLimit(-1) now returns:", debug.SetMemoryLimit(-1))
	fmt.Println("SetGCPercent(100) returned the -1 that was in force:", debug.SetGCPercent(100))
}
```

```bash
#!/usr/bin/env bash
# GOGC and GOMEMLIMIT are read once, when the program starts. The program
# asks the runtime what it read: SetGCPercent(100) returns the value that was
# in force, and SetMemoryLimit(-1) returns the limit without changing it.
set -u
export GOTOOLCHAIN=local

dir=$(mktemp -d)
trap 'rm -rf "$dir"' EXIT

cat >"$dir/settings.go" <<'GO'
package main

import (
	"fmt"
	"runtime/debug"
)

func main() {
	fmt.Println("GC percent at startup:", debug.SetGCPercent(100))
	fmt.Println("memory limit at startup:", debug.SetMemoryLimit(-1))
}
GO

say() { printf '$ %s\n' "$*"; }

say 'go build settings.go'
(cd "$dir" && go build settings.go) || exit 1

say './settings'
(cd "$dir" && env -u GOGC -u GOMEMLIMIT ./settings)
say 'GOGC=50 ./settings'
(cd "$dir" && GOGC=50 ./settings)
say 'GOGC=off ./settings'
(cd "$dir" && GOGC=off ./settings)
say 'GOMEMLIMIT=64MiB ./settings'
(cd "$dir" && GOMEMLIMIT=64MiB ./settings)
say 'GOGC=off GOMEMLIMIT=1GiB ./settings'
(cd "$dir" && GOGC=off GOMEMLIMIT=1GiB ./settings)
echo "exit status $?"
```

## What to do

- **Leave `GOGC` at 100 until a profile says otherwise.** Raising it trades memory for CPU; lowering it the other way. The [GC guide ↗](https://go.dev/doc/gc-guide#GOGC) has the model and the interactive graphs.
- **Set `GOMEMLIMIT` when the program owns a known amount of memory** — a container with a cap, a machine it has to itself — and leave a margin below the cap for what the limit does not count. The guide's [suggested uses ↗](https://go.dev/doc/gc-guide#Suggested_uses) also list when not to: memory shared with other programs, or a limit the deployment cannot honour.
- **Never `GOGC=off` without a limit** outside a benchmark or a short batch job that will exit anyway.
- **Set from the environment, not from code**, unless the program is the one that knows its budget; and when a library must change a setting, restore what it found, on every path out.
- **Look before tuning**: `GODEBUG=gctrace=1` for a quick view, [`runtime/metrics` ↗](https://pkg.go.dev/runtime/metrics) for a program that watches itself, and [A CPU profile names the hot function](../../15_Performance/a_cpu_profile_names_the_hot_function/README.md) when the collector is that function.

```go
// Kata: write withCollectorOff(f), which turns the collector off while f
// runs and restores the previous setting afterwards, even if f panics.
// Inside f, allocate 128 MiB of garbage and show that no collection ran;
// afterwards, show that the percentage is back to what it was.
//
//	go build gogc_and_gomemlimit_tune_the_collector_kata_go.go && ./gogc_and_gomemlimit_tune_the_collector_kata_go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
)

func numGC() uint32 {
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	return m.NumGC
}

// withCollectorOff runs f with GC percent -1 and restores the previous
// setting on every way out, including a panic in f.
func withCollectorOff(f func()) {
	previous := debug.SetGCPercent(-1)
	defer debug.SetGCPercent(previous)
	f()
}

var slab []byte

func main() {
	fmt.Println("percent before:", debug.SetGCPercent(100))

	withCollectorOff(func() {
		fmt.Println("inside: SetGCPercent(-1) reads back", debug.SetGCPercent(-1))
		before := numGC()
		for range 128 {
			slab = make([]byte, 1<<20)
		}
		slab = nil
		fmt.Println("inside: 128 MiB of garbage ran a collection:", numGC() > before)
	})
	fmt.Println("after: percent restored to 100:", debug.SetGCPercent(100) == 100)

	func() {
		defer func() { recover() }()
		withCollectorOff(func() { panic("the work failed") })
	}()
	fmt.Println("after a panic inside: percent restored to 100:", debug.SetGCPercent(100) == 100)
}
```

## In other languages

- **Rust** — there is no collector to tune: memory goes back when its owner is dropped, at a point the code determines, which the Rust library's [Assignment drops the old value ↗](https://masiarek.github.io/rust-learning-library/18_Ownership/assignment_is_a_drop/index.html) pins down; [What a smart pointer costs ↗](https://masiarek.github.io/rust-learning-library/41_Smart_Pointers/what_a_smart_pointer_costs/index.html) is the price paid instead of a collector's.
- **Python** — reference counts free most objects at once and the [`gc` module ↗](https://docs.python.org/3/library/gc.html) collects the cycles, with `gc.set_threshold` as the knob; there is no memory limit, and `gc.disable()` is Python's `GOGC=off`.
- **Java** — [`-Xmx` ↗](https://docs.oracle.com/en/java/javase/21/docs/specs/man/java.html) is a hard ceiling that ends the program with `OutOfMemoryError`; Go's limit is soft, and the runtime lets the heap pass it rather than stop.
