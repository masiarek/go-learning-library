# Escape analysis decides stack or heap

**Level:** 301 · anyone who has been told that pointers are slow, or that they are fast, and wants to see the compiler's actual decision

**One line:** Go has no rule that `new` or `&` means the heap: the compiler keeps a value in its function's frame unless the value's address may outlive the call or lands somewhere the compiler cannot follow — a returned pointer, an interface, a closure that is returned, a slice too big for a frame — and `go build -gcflags=-m` prints that decision for every value, while `testing.AllocsPerRun` counts what it cost.

A fixed file holds one function per classic cause. `total` builds an `Order` and drops it; `newOrder` returns `&o`; `show` passes an `Order` to `fmt.Println`; `counter` returns a closure over `n`; `sumSmall` and `sumBig` make a slice of a constant size, 8,000 bytes and 800,000 bytes. The driver builds the file with `-gcflags=-m` and keeps the lines that say where a value went:

## Reading the output

**No line for `total`'s `o`.** The lines name what left a frame. The `Order` built in `total` is used and dropped inside the call, so escape analysis has nothing to say about it, and it lives in `total`'s frame. That is the default; the heap is the exception the compiler has to justify.

**`moved to heap: o` — a pointer to a local is returned.** `newOrder` returns `&o`, and the caller will use that address after `newOrder`'s frame is gone. A frame is copied when the stack grows ([A goroutine stack grows and has a limit](../a_goroutine_stack_grows_and_has_a_limit/README.md)) and reused by the next call, so a pointer into it cannot be allowed out: the variable is allocated on the heap instead. The [Go FAQ ↗](https://go.dev/doc/faq#stack_or_heap) states the rule — if the compiler cannot prove that the variable is not referenced after the function returns, it allocates the variable on the garbage-collected heap.

**`o escapes to heap` — a value passed to `fmt.Println`.** `show` copies its `Order` into an `any`, because that is `Println`'s parameter type, and an interface value carries a pointer to its data ([An interface is two words](../../11_Interfaces_and_Method_Sets/an_interface_is_two_words/README.md)). `Println` hands that data on to code the compiler does not follow, so the copy is made on the heap. The line above it, `... argument does not escape`, is about the `[]any` that carries the arguments: `fmt` is written so that this slice can stay in the caller's frame, so the cost is one allocation for the `Order`, not two.

**`moved to heap: n` and `func literal escapes to heap` — a closure that outlives the frame.** `counter` returns a function that still increments `n`, so `n` must survive `counter`, and so must the closure object that points at it. Two allocations, as the second program counts.

**`make([]int, 1000) does not escape`, but `make([]int, 100000) escapes to heap`.** Both sizes are constants, so the compiler knows exactly how many bytes each needs. 8,000 bytes goes in the frame; 800,000 does not, because the compiler puts an implicit allocation of known size in a frame only up to 64 KB (`MaxImplicitStackVarSize` in [`cmd/compile/internal/ir/cfg.go` ↗](https://github.com/golang/go/blob/go1.25.5/src/cmd/compile/internal/ir/cfg.go); an explicit `var` gets 128 KB). Above that, the backing array is heap memory even though nothing keeps it.

**Positions and wording.** `./orders.go:24:2` is the line and column of the variable, stable because the file is fixed. The vocabulary — `moved to heap`, `escapes to heap`, `does not escape`, and the `leaking param` lines this driver filtered out — is listed on [Memory: what go vet and gofmt catch](../memory_vet_and_lints/README.md). A later compiler may reword any of it; the recorded key is go1.25's.

**0, 1, 2.** The `Order` used in one frame costs nothing; the returned pointer costs one allocation; the closure costs two, `n` and the closure itself.

**An `int64` in an interface: 1 for 1000, 0 for 7.** Storing a value in an interface is one of the escapes above, and it costs an allocation — unless the value is small. The runtime keeps a table of the integers 0 to 255 ([`staticuint64s`, used by the `convT` functions in `runtime/iface.go` ↗](https://github.com/golang/go/blob/go1.25.5/src/runtime/iface.go)) and points the interface at that instead. The program computes both values at run time on purpose: for a constant, the compiler builds the interface's data at compile time and the count is 0 whatever the value. *(Not machine-checked here.)*

**`make([]int, n)` at run time: 0 for `n = 4`, 1 for `n = 1000`.** `-m` says `make([]int, n) does not escape` for both, and both are true: since Go 1.25 the compiler reserves a small buffer in the frame for a slice whose size is not a constant, uses it when the slice fits, and goes to the heap otherwise ([Go 1.25 release notes ↗](https://go.dev/doc/go1.25#compiler)). Four ints fit; a thousand do not. The threshold is the compiler's business and is not on this page.

**`append` past the capacity: 1.** Four appends into a slice with room for four stay in the frame. The fifth has to grow the slice, and growing means a new backing array from the allocator, on the heap, however small. No `-m` line announces it, because it is not an escape: the slice header never left the frame, but its data had to.

```bash
#!/usr/bin/env bash
# go build -gcflags=-m prints one line for each decision escape analysis made.
# This script builds a fixed file and keeps only the lines that say where a
# value went: "moved to heap", "escapes to heap" and "does not escape". Every
# function is marked //go:noinline, so that main's inlined copies do not add
# a second verdict for each of them; the positions are stable because the
# file is fixed.
set -u
export GOTOOLCHAIN=local

dir=$(mktemp -d)
trap 'rm -rf "$dir"' EXIT

cat >"$dir/orders.go" <<'GO'
package main

import "fmt"

// Order is 24 bytes: small enough for any frame.
type Order struct {
	ID    int
	Qty   int
	Price int
}

// total builds an Order and lets it go: the Order stays in this frame.
//
//go:noinline
func total(qty, price int) int {
	o := Order{Qty: qty, Price: price}
	return o.Qty * o.Price
}

// newOrder returns the address of a local: the local is moved to the heap.
//
//go:noinline
func newOrder(id int) *Order {
	o := Order{ID: id}
	return &o
}

// show hands o to fmt.Println, which takes it as an interface value.
//
//go:noinline
func show(o Order) {
	fmt.Println(o)
}

// counter returns a closure that outlives this frame and still uses n.
//
//go:noinline
func counter() func() int {
	n := 0
	return func() int { n++; return n }
}

// sumSmall's slice has a constant size of 8,000 bytes: it fits in a frame.
//
//go:noinline
func sumSmall() int {
	s := make([]int, 1000)
	for i := range s {
		s[i] = i
	}
	return s[999]
}

// sumBig's slice has a constant size too, but 800,000 bytes is more than
// the compiler will put in a frame.
//
//go:noinline
func sumBig() int {
	s := make([]int, 100000)
	for i := range s {
		s[i] = i
	}
	return s[99999]
}

func main() {
	next := counter()
	show(Order{ID: total(3, 7) + newOrder(1).ID + next() + sumSmall() + sumBig()})
}
GO

say() { printf '$ %s\n' "$*"; }

say 'go build -gcflags=-m orders.go 2>&1 | grep -E "moved to heap|escapes to heap|does not escape"'
(cd "$dir" && go build -gcflags=-m orders.go 2>&1) | grep -E 'moved to heap|escapes to heap|does not escape'
echo "exit status ${PIPESTATUS[0]}"
```

```go
// testing.AllocsPerRun counts heap allocations per call of a function, so a
// program can check what -gcflags=-m claimed: 0 for a value that stays in
// its frame, 1 for each value the compiler moved to the heap, and the cases
// -m cannot see because they are decided at run time.
//
//	go build escape_analysis_decides_stack_or_heap_go.go && ./escape_analysis_decides_stack_or_heap_go
package main

import (
	"fmt"
	"os"
	"testing"
)

// Order is 24 bytes: small enough for any frame.
type Order struct {
	ID    int
	Qty   int
	Price int
}

// Package-level sinks: a store into one is a use the compiler cannot see past.
var (
	lastOrder *Order
	lastValue any
	total     int
)

// newOrder returns the address of a local: the local is moved to the heap.
//
//go:noinline
func newOrder(id int) *Order {
	o := Order{ID: id}
	return &o
}

// counter returns a closure that outlives this frame and still uses n.
//
//go:noinline
func counter() func() int {
	n := 0
	return func() int { n++; return n }
}

func main() {
	report := func(what string, f func()) {
		fmt.Printf("%-50s %v\n", what, testing.AllocsPerRun(100, f))
	}

	report("an Order built, used and dropped in one frame:", func() {
		o := Order{Qty: 3, Price: 7}
		total += o.Qty * o.Price
	})
	report("a pointer to a local, returned and stored:", func() {
		lastOrder = newOrder(1)
	})
	report("a closure that captures its counter:", func() {
		next := counter()
		total += next()
	})

	// Values computed at run time, so the compiler cannot pre-build the
	// interface value for them the way it does for a constant.
	big := int64(len(os.Args)) + 999
	small := int64(len(os.Args)) + 6
	report("an int64 of 1000 stored in an interface:", func() { lastValue = big })
	report("an int64 of 7 stored in an interface:", func() { lastValue = small })

	report("make([]int, 1000), constant size, used here:", func() {
		s := make([]int, 1000)
		total += s[999]
	})
	report("make([]int, 100000), constant size, used here:", func() {
		s := make([]int, 100000)
		total += s[99999]
	})
	n := 4
	report("make([]int, n) with n = 4 at run time:", func() {
		s := make([]int, n)
		total += s[n-1]
	})
	n = 1000
	report("make([]int, n) with n = 1000 at run time:", func() {
		s := make([]int, n)
		total += s[n-1]
	})

	report("append 4 orders to a slice with room for 4:", func() {
		s := make([]int, 0, 4)
		for i := range 4 {
			s = append(s, i)
		}
		total += s[3]
	})
	report("append 5 orders to a slice with room for 4:", func() {
		s := make([]int, 0, 4)
		for i := range 5 {
			s = append(s, i)
		}
		total += s[4]
	})
}
```

## What to do

- **Read `-m` before guessing.** `go build -gcflags=-m ./...` prints every decision in a package; `-m=2` adds the chain of reasons (`flow: {heap} ← ...`). Inlining changes the answers, which is why the driver marks its functions `//go:noinline`; [The compiler says what it inlines](../../15_Performance/the_compiler_says_what_it_inlines/README.md) is the other half of that output.
- **Return small structs by value when the caller only reads them.** The kata below measures it: 24 bytes copied is cheaper than 24 bytes allocated, traced and collected.
- **Keep hot-path values out of interfaces** where they do not need to be: `fmt.Sprintf` and `log.Printf` box every argument. [Allocs/op is a key, ns/op is not](../../15_Performance/allocs_per_op_is_a_key_ns_per_op_is_not/README.md) makes the allocation count the number to watch.
- **Give a slice its capacity up front** when the length is known — `make([]T, 0, n)` — to avoid the growth allocations that `-m` never mentions.
- **Do not fight the compiler on principle.** One allocation per request is invisible; one per byte is not. Measure with [`AllocsPerRun`](../../15_Performance/allocsperrun_counts_allocations/README.md) or a benchmark first.

## Practice

An invoice lookup builds an `Invoice` on the spot and returns `*Invoice`; every caller reads two fields and drops it. Write the lookup both ways — returning a pointer, and returning the struct by value — mark both `//go:noinline` so that you measure the functions and not what `main` inlined, and use `testing.AllocsPerRun` to show that the pointer version allocates once per call and the value version never.
```go
// Kata: an invoice lookup returns *Invoice for a value it builds on the spot,
// and its callers only read two fields. Return the Invoice by value instead,
// and prove with testing.AllocsPerRun that the pointer version allocates once
// per call and the value version not at all.
//
//	go build escape_analysis_decides_stack_or_heap_kata_go.go && ./escape_analysis_decides_stack_or_heap_kata_go
package main

import (
	"fmt"
	"testing"
)

type Invoice struct {
	Number int
	Cents  int64
	Paid   bool
}

var pointerCents, valueCents int64

// lookupPointer's inv is moved to the heap: its address leaves the frame.
//
//go:noinline
func lookupPointer(number int) *Invoice {
	inv := Invoice{Number: number, Cents: int64(number) * 250}
	return &inv
}

// lookupValue copies 24 bytes into the caller's frame instead.
//
//go:noinline
func lookupValue(number int) Invoice {
	inv := Invoice{Number: number, Cents: int64(number) * 250}
	return inv
}

func main() {
	fmt.Println("pointer version, allocations per call:", testing.AllocsPerRun(1000, func() {
		inv := lookupPointer(42)
		pointerCents += inv.Cents
	}))
	fmt.Println("value version, allocations per call:  ", testing.AllocsPerRun(1000, func() {
		inv := lookupValue(42)
		valueCents += inv.Cents
	}))
	fmt.Println("both versions summed the same cents:", pointerCents == valueCents)
}
```

## In other languages

- **Rust** — the Rust library's [Stack and heap ↗](https://masiarek.github.io/rust-learning-library/18_Ownership/stack_and_heap/index.html): Rust decides by type, not by analysis — a `Box<T>`, a `Vec<T>` or a `String` is heap memory because the type says so, and a plain struct is on the stack because nothing moves it. Returning a reference to a local is a compile error there, where Go silently moves the local to the heap; [Returned by value ↗](https://masiarek.github.io/rust-learning-library/18_Ownership/returned_by_value/index.html) measures what a returned struct costs in Rust.
- **C** — there is no escape analysis: a local is on the stack, and returning its address is undefined behaviour the compiler may or may not warn about. The C library's [Reading the memory map ↗](https://masiarek.github.io/c-learning-library/02_Decompiling/reading_the_memory_map/index.html) shows where the stack, the heap and the data segments of a running program sit.
- **Concurrency library** — [Can a thread borrow a local variable? ↗](https://masiarek.github.io/concurrency-learning-library/01_Threads/lending_a_local_to_a_thread/index.html) puts the closure case to six languages; Go's answer is this page's `moved to heap: n`.
